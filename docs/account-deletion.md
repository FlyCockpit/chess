# Account deletion

Account deletion establishes a durable **pending** access fence, then completes physical erasure in bounded retryable worker phases. The security settings page accepts deletion after a fresh primary sign-in and typed confirmation. Admin `users.remove` follows the same path and returns pending instead of cascading the account. Acceptance always says `complete:false`; it does not promise that live resources or physical cleanup have finished.

The request checks that the external register is provisioned and accessible before accepting new destructive intent; unavailable configuration leaves the account unchanged and returns actionable refusal. The self request is cookie-only, protected by the existing second-factor policy and its own fail-closed rate budget. It accepts exactly the typed `DELETE` confirmation and derives the account from the session. A live, non-impersonated browser session must carry server-owned `authenticatedAt` proof from primary password or identity-provider authentication within five minutes; its creation time is not proof. Factor enrollment and cookie rotations preserve the parent proof, and sign-in code completion preserves the original password proof time. Password and SSO users both sign in again when stale; missing proof requires a new sign-in. The committing authority transaction rechecks the shared forced-second-factor policy after owner-lock waits, retaining its existing defaults and enrollment grace. Every administrator must first transfer their authority. The shared last-active-admin guard also protects admin-initiated removal and excludes deletion-pending accounts from usable-admin counts.

The request takes password-write → CLI-credential → set-password-link → hosted-admission locks before opening its short Serializable admin-removal snapshot. That transaction records `deletionRequestedAt` and `deletionState=pending`, revokes sessions/API keys/device approvals/runner authority, and removes the sealed OpenRouter connection atomically. It deliberately never reads or writes `chess_match`, so continuous heartbeats and an already-admitted move cannot invalidate the authority/fence snapshot. The original at-most-three retries and deadline remain for genuine concurrent authority changes; each attempt rechecks live authority and recent authentication.

After that durable fence commits, the outer ReadCommitted transaction stops active matches as `owner-delete`, clears human turns and settles official withdrawals before releasing the locks or answering. Runner matches are scanned in keyset pages of 50; each successful active-row stop also clears its generation/resume deadline, sets runner state to stopped, advances its revision and cancels outstanding commands in the same transaction. Existing terminal rows remain unchanged. Worker persistence, preparation and reconciliation take the same credential lock before checking the owner: they finish before the fence, or refuse the old archive and settle `owner-delete` afterwards. The heartbeat also drops pending owners. A bounded pending-owner reconciliation sweep covers hosted and runner matches before archive validation, queue inspection or human wake repair, so invalid archives or unavailable Redis cannot strand deletion intent. Previously admitted stop, disconnect and credential-reset cancellations preserve `owner-delete` after the pending fence under the common credential ordering. This preserves all accepted official starts without letting a late model result replace the withdrawal. If a crash or database failure prevents request-side match settlement after the fence committed, the pending marker and revocations remain durable; worker/reconcile cancellation and D2b can resume cleanup. A retry retains the original timestamp/cleanup phase and repeats idempotent match settlement. Failed fence transactions still roll back acceptance. Before returning acceptance, the request fsyncs its purpose-bound suppression identifier to `ACCOUNT_DELETION_REGISTER_DIR`, independently of any database snapshot. If that fails after the access fence committed, the request reports `CLEANUP_UNAVAILABLE`: access remains blocked and cleanup retries; the UI acknowledges pending cleanup without claiming success. A successful response states `complete:false`; session revocation signs the requester out. There is no unauthenticated status receipt or external email link.

Every later credential mint, callback, hosted admission, move and actual provider request must recheck active account authority under its relevant lock. This includes key introspection from connection status: a captured key or live lease cannot start HTTP after the pending fence, and a credential-lock wait cannot renew its original lease/provider deadline. Runner transport checks the authoritative `isOwnerActive(userId)` on connect, messages and heartbeat. A key request admitted before the fence may remain in flight: D2b must stop/confirm all such leases and sockets before claiming completion. Removing a locally stored key does not revoke that key at OpenRouter; the user must also revoke it at OpenRouter's key settings if desired.

Published rows are hidden while their owner is pending. The retained replay scrubber processes at most 50 rows per keyset batch and detaches ownership only with a sanitized archive. It rotates neutral slugs and public IDs, drops old identity-bearing URLs, title and names, raw replies, remarks, comments, tool text and archive IDs. It retains legal moves/board, trusted catalog model identifiers, prompt/settings and numerical results. Cleanup reads only the existing trusted catalog cache and never starts upstream requests; a cold cache uses neutral model labels. Null-owner public reads sanitize again; exported JSON/PNG/MP4 use the same projection. Sanitization never changes publication/moderation state. Private replay removal is explicit cleanup; nullable ownership uses `SetNull` rather than a cascade. Minimal owner-independent official commitments survive both private and published cleanup.

D2c is a separate signed-in, rate-limited, step-up-protected streamed JSON/PGN download. It must include account metadata, private and published games, safe OpenRouter metadata, runner machines and reports filed. It must clean up mailed-reset Verification JSON during later deletion and never export keys or authentication proofs. The export endpoint is independent of deletion; it is unavailable after the pending fence. Deletion has no unauthenticated status receipt or emailed capability. A fixed login-page acknowledgement is display-only, cannot query account state and cannot prove completion.

## Bounded physical completion

The existing minute chess-reconcile job settles pending-owner matches first, then advances at most five deletion-pending accounts by one bounded phase each. A process cursor wraps so a blocked account cannot starve peers. The deletion transaction takes the existing password-write → CLI-credential → set-password-link → admission locks. Progress uses the existing `pending`/`cleaning` lifecycle; `cleaning` carries one strict JSON cursor `{phase,afterId}`, with no migration or alternate cursor shape. Each phase rechecks durable intent and fsyncs the external suppression record before destructive progress; a crash or missing storage never clears the fence.

1. `pending`: stop up to50 active matches as owner-delete and cancel outstanding runner commands, recovering a crash after request-side fence commit.
2. `stopping`: wait at least180seconds after the request, longer than admitted publication deadlines and self-fencing resource lifetimes; require no live key-use leases and no runner socket leases in pages of50 machines. A restarted/unavailable/malformed Redis store cannot prove stop. Native runner socket leases are released when the socket finishes, not when close is requested. Generation, durable account checks and local lease fences cover missed invalidations; cleanup never deletes a lease to pretend termination.
3. `matches`: remove deterministic BullMQ jobs and retained results through their per-match registry, at most10 entries per purge; active/ambiguous work keeps cleanup pending. Exact indexed job IDs also remove their completed/failed/remove events from bounded queue event-stream snapshots before the index is forgotten, preserving other users' events. Publishers recheck owner/visibility while holding the credential lock through publication and index jobs before enqueue. Each underlying BullMQ mutation checks a random retirement epoch and indexes itself atomically in Redis; purging rotates that epoch, and a missing epoch refuses old writes after a restart. Delayed native commands cannot reinsert private jobs or their event data after a client timeout and erasure. Only a purpose-bound hashed retirement fence remains, without raw account/match identity. For each cleared batch of at most50 matches, delete private rows, remove all runner command/event payloads from retained published rows, then apply D2a's strict whitelist anonymization to exactly those cleared rows. Hidden publication stays hidden, old URLs disappear, and permanent official commitments survive. Unsupported/corrupt published archives keep deletion pending for repair; raw data is never detached and exposed.
4. `verifications`: delete at most100 owned non-FK records, repeating until drained before removing pre-delete machine IDs. Current formats include reset/mailed-reset JSON, 2FA challenge/OTP/attempt/trust records, owned OAuth link state, runner operating states, proof JSON and owner-bearing TOTP fences. Email-verification JWTs are user-ID-bound and cannot authorize a replacement account. Owned proof creation itself takes the credential lock and rechecks live owner/challenge/session on the insertion transaction; elapsed quiet time is never proof against a paused writer. Unbound OAuth state and inaccessible Redis PKCE state expire by bounded TTL behind the durable fence.
5. `finalizing`: repeat the residual match/Verification inventory and key-use stop check, atomically retire its Redis revoked-key cache writer and clear its hash history, then delete User and its FK-owned account/2FA/session/key/device/machine/claim/reporter records in one transaction. A retry with an absent User is complete. No background job carries provider keys or personal payloads. Revocation-cache writes also carry the original owner-lock deadline and an atomic random epoch guard; retired or missing epochs reject delayed native commands, so an old disconnect cannot recreate account-linked hash history. Only the purpose-bound hashed retirement marker remains.

The restricted v2 chained register contains a purpose-bound SHA256 subject hash, request time, retention review date and sequence/previous/current digests; it is not anonymous public statistics. It lives on separately mounted persistent storage shared by request processes/workers and guarded restore, outside DB snapshots. Its31day minimum covers the30day backup policy, but the entire chain is retained while any older backup remains restorable; individual records are never pruned. Protect the complete-current copy and latest head independently through every accepted deletion. Restore requires exact equality to that independently trusted current head and ancestry of its backup checkpoint; missing current evidence refuses recovery. A missing or stale register cannot safely be reconstructed from an old database dump. See [Backup and restore](./backup-restore.md#account-erasure-suppression) for the mount/restore contract.

Guarded restore validates the external register and reapplies revocations, match cancellation and pending visibility fences in the same transaction as restored data, before COMMIT/admission. Restored suppressed users remain pending until this same worker completes erasure; restoring an old dump never restores their keys, sessions, runner authority or published identity. Operational logs, previously sent mail, remote provider keys, user-owned runner disks and already downloaded files follow their separate retention/ownership rules.
