# Design system

This app follows the FlyCockpit template's design system (`patterns/design-system.md` in the template repo). This file records only where Cockpit Chess differs from it or goes further.

## Edge lines

These are the horizontal edges every container sits on, measured on ink: glyph and icon bounds, or a boxed control's box. Change a value only with the owner's approval, and record the new value here.

Terms: the **text line** is where labels, headings and bare icons start. The **box line** is where filled, bordered or shadowed controls start. The **trailing line** is where the last item in a row ends. An item is within tolerance when its ink is within 1px of its line.

Two rules decide the cases the tables do not list:

- **Boxes share the text line** inside pages, cards, panels and forms. A box does not outdent by its own padding. Ghost icon buttons are centred items, not edge items.
- **Fix a miss in the container**: its padding, a shared inset (`inset`, `--cc-panel-inset`, `px-*` on a track), or the shared component's placement. Never fix one item with a one-off margin.

Five more rules, from the template's back-port of the apps' passes (11-22):

- **An edge text item puts its label on the box's edge.** When a text link or button is the first or last item on a line and its box is wider than its label (a 44px minimum box around a short label), start-align the label for a leading item and end-align it for a trailing one. Centring is for items in centred bars, such as BottomNav, and for icon buttons. The arena nav below follows this.
- **Table text sits on its container's text line.** The first and last cells drop their outer padding (or take the container's inset). Inner cell padding separates columns; it must not indent the first column from the heading above the table. The leaderboard below follows this.
- **Overriding a Button's padding: override every breakpoint.** tailwind-merge treats `px-*` and `md:px-*` as separate groups, so a `className="px-2"` on a Button whose size carries a responsive padding leaves the `md:` value in force. Write both (`px-2 md:px-2`).
- **A control flush with a clipping edge draws its focus ring inside its box** (`focus-visible:ring-inset focus-visible:ring-offset-0`). Button's ring is drawn outside the box, and the viewport or an `overflow-*-hidden` ancestor cuts it off.
- **Frame bands keep the frame line.** Banners above the page (`AdminSetupBanner`) and the header sit 16px inside the frame at every width. They are not re-aligned to a narrower page container below them.

## Shell rules

The template's four shell rules (`patterns/design-system.md` § Shell rules in the template repo), as they apply here. Every page meets them, in both themes and at every width. `pnpm policy:checks` enforces what a static check can (rules G8 and G9 in `scripts/check-web-conventions.ts`, gate 4 of `scripts/check-agent-rules.ts`); `apps/web/src/components/public-shell.test.tsx`, `apps/web/src/lib/theme-contrast.test.ts` and `apps/web/src/theme.test.ts` pin the markup and the tokens; `pnpm check:layout --url <web dev server>` measures the geometry in a browser (it needs `agent-browser`; `--login <email>` with `CHECK_LAYOUT_PASSWORD` adds the signed-in pages). It is not part of CI.

1. **The footer sits at the bottom of a short page.** The arena's public shell (`apps/web/src/components/public-shell.tsx`, used by the `_public` layout and the 404) owns the one public footer (`components/public-footer.tsx`: the disclaimer, the AI disclosure and Cookie preferences). Inside `<main>`, the content is one `flex min-h-full flex-col` column: the routed page grows (`flex-1`) and the footer comes last, so on a short page (The rules, an empty leaderboard or studio) the footer's bottom is the scroller's bottom, and on a long page it follows the content. No `position: fixed` footer, no second scroller, and no `<footer>` in a route file or an arena tab: footer content goes into `PublicFooter`. `.cc-app` carries no bottom padding; the footer row's own padding ends the page. The CLI local lab (`components/chess/local-model-lab.tsx`) puts its own footer (the local-only note and its address) in the same column. The app shell (`_app`) has no footer: phones get the BottomNav, Cookie preferences sits in Settings.
2. **Full-bleed dividers span the viewport.** The arena header's rule (`.cc-header`), the footer's rule (`.cc-footer`), the app header's `<hr>`, the admin sub-nav and the setup banners reach from 0 to the viewport's right edge at every width, also past 1440px: the arena header's border sits on the full-width header and only its row (`.cc-header-row`) is capped; the footer's rule is full width and its text keeps the `.cc-app` column. On a page that scrolls, rules inside `<main>` meet its visible scrollbar. That is why no `<main>` (arena, app shell, local lab) reserves a scrollbar gutter: with classic scrollbars (Windows, Linux) a stable gutter is an empty 15px strip that every rule inside the scroller stops short of. The cost is that centred content moves by half a scrollbar when a page grows past the viewport on those platforms; overlays lock the document, not `<main>`.
3. **No surface ignores the theme.** The theme is the stored choice, else the OS, applied as the `.dark` class before first paint (`packages/config/src/theme-init.ts`); the CLI local lab has no toggle and so no stored choice, and follows the OS live (`apps/web/src/local.tsx`). Every surface uses the tokens in `packages/ui/src/styles/globals.css` and `dark:` variants, never a `prefers-color-scheme` query or a literal colour; a new colour becomes a token there. That includes the arena palette (`--cc-*`, light on `:root`, dark on `.dark`) and the dark arena's shadcn overrides (`.dark .cc-public-shell`). The deliberately fixed colours in `apps/web/src/index.css` (board squares and pieces, the hero board art, and the White/Black depictions: avatars, swatches, the evaluation bar and graph, remark bubbles, result marks) carry a `theme-exempt: <reason>` comment on their line, which G9 requires; the share image and video frames are drawn on a canvas and are not CSS. A CSS `url(#id)` is an element reference, not a colour. Toasts are a popover surface: `globals.css` fills sileo's pill with `--popover`, writes the title in `--popover-foreground` and maps sileo's state colours to `--state-*`, `--destructive` and, for the action state, `--state-info` (dark `--primary` is a button fill, too dark for text on the dark popover); the Toaster gets no `theme` prop (sileo's themes invert the page). Text and state colours reach 4.5:1 on the surface they sit on in both themes.
4. **Every route renders inside a shell, the 404 included.** An unknown URL matches no layout, so `$lang`'s `notFoundComponent` (`PublicNotFoundPage`) wraps the not-found body in the public shell: header with language and theme controls, footer, scroller. The router's `defaultNotFoundComponent` (`NotFoundPage`) is the body alone, for a route that sets its own boundary inside a shell. A `notFound()` thrown by a route without its own `notFoundComponent` lands on the same public 404. Fixed chrome follows the shell it belongs to: the cookie banner reserves room for the BottomNav only while one is mounted (`data-bottom-nav`).

## Layer scale

The app keeps the template's layer scale (`patterns/design-system.md` in the template repo). It is recorded here because the cookie banner once sat at `z-[60]`, above the overlays, and covered a row-actions menu opened near the bottom of `/admin/users`. The banner, the BottomNav and every portal sit on the root stacking context, so these numbers compete directly. That holds only while none of them has an ancestor that opens its own stacking context (`isolate`, a `z-*` on a positioned element, `transform`, `filter`, `backdrop-filter`, `opacity` below 1, `will-change`, `contain`), so fixed chrome mounts at the shell or root level. A portaled popup competes through its outermost part (Positioner, Backdrop/Overlay, Viewport):

| Layer | Who |
|---|---|
| `z-10`, `z-20` (and `-z-1`), small CSS values (the board's `.cc-*` cells and badges at 1–4) | Inside a component; never used to beat app chrome |
| `z-30` | Sticky page chrome |
| `z-40` | Non-modal fixed chrome over the page: the cookie banner. Below every overlay, so an open menu, select, popover, combobox, dialog, sheet, drawer or toast is never covered; below the BottomNav, which paints over the banner's bottom padding |
| `z-50` | The overlay layer: the `packages/ui` portals (dropdown menu, select, popover, dialog, alert dialog, sheet, drawer), the sileo toast viewport, the mobile BottomNav and the focused skip links |

Nothing goes above `z-50`. Utilities use only the steps above (`-z-1`, `z-10`, `z-20`, `z-30`, `z-40`, `z-50`): no arbitrary `z-[…]` / `z-(…)` values and no other numbers. Every overlay root carries an unconditional `z-50` (a responsive-only `md:z-50` leaves phones without a layer). A new banner, tray or floating button is `z-40` or lower and reserves its own space, as the banner does with `--consent-inset`.

What checks it:

- `apps/web/src/components/consent/consent-layers.test.tsx` is the safety net. It renders the banner and checks its layer against every portaled overlay in `packages/ui/src` (read from the components, so a new overlay is covered), the sileo toast viewport and the BottomNav, and that no overlay is lowered below `z-50` through the `className` it is given (in app code or a shared wrapper such as `CommandDialog`).
- `pnpm policy:checks` is a line grep for the obvious cases: an off-scale `z-…` utility in `apps/web/src` or `packages/ui/src` (markup, class strings, `@apply`).
- Neither catches: custom CSS classes and stylesheets (`.my-sheet { z-index: 30 }`, a `[data-slot=…]` rule, however its selector is spaced, nested `@media` blocks), CSS `z-index` declarations and inline `style` / `zIndex`, class names built at runtime (`` `z-${n}` ``) or held in a constant, layers set through pseudo-element or descendant variants (`before:`, `*:`, `[&…]:`, which the test skips), and an ancestor that opens its own stacking context. Those are review items; real hit-testing needs a browser.
