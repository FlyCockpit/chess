# Design system

This app follows the FlyCockpit template's design system (`patterns/design-system.md` in the template repo). This file records only where Cockpit Chess differs from it or goes further.

## Edge lines

These are the horizontal edges every container sits on, measured on ink: glyph and icon bounds, or a boxed control's box. Change a value only with the owner's approval, and record the new value here.

Terms: the **text line** is where labels, headings and bare icons start. The **box line** is where filled, bordered or shadowed controls start. The **trailing line** is where the last item in a row ends. An item is within tolerance when its ink is within 1px of its line.

Two rules decide the cases the tables do not list:

- **Boxes share the text line** inside pages, cards, panels and forms. A box does not outdent by its own padding. Ghost icon buttons are centred items, not edge items.
- **Fix a miss in the container**: its padding, a shared inset (`inset`, `--cc-panel-inset`, `px-*` on a track), or the shared component's placement. Never fix one item with a one-off margin.

Five more rules, from the template's back-port of the apps' passes (11-22):

- **An edge text item puts its label on the box's edge.** When a text link or button is the first or last item on a line and its box is wider than its label (a 44px minimum box around a short label), start-align the label for a leading item and end-align it for a trailing one. Centring is for items in centred bars, such as BottomNav, and for icon buttons. The arena nav below follows this.
- **Table text sits on its container's text line.** The first and last cells drop their outer padding (or take the container's inset). Inner cell padding separates columns; it must not indent the first column from the heading above the table. The leaderboard below follows this.
- **Overriding a Button's padding: override every breakpoint.** tailwind-merge treats `px-*` and `md:px-*` as separate groups, so a `className="px-2"` on a Button whose size carries a responsive padding leaves the `md:` value in force. Write both (`px-2 md:px-2`).
- **A control flush with a clipping edge draws its focus ring inside its box** (`focus-visible:ring-inset focus-visible:ring-offset-0`). Button's ring is drawn outside the box, and the viewport or an `overflow-*-hidden` ancestor cuts it off.
- **Frame bands keep the frame line.** Banners above the page (`AdminSetupBanner`) and the header sit 16px inside the frame at every width. They are not re-aligned to a narrower page container below them.

## Shell rules

The template's four shell rules (`patterns/design-system.md` § Shell rules in the template repo), as they apply here. Every page meets them, in both themes and at every width. `pnpm policy:checks` enforces what a static check can (rules G8 and G9 in `scripts/check-web-conventions.ts`, gate 4 of `scripts/check-agent-rules.ts`); `apps/web/src/components/public-shell.test.tsx`, `apps/web/src/lib/theme-contrast.test.ts` and `apps/web/src/theme.test.ts` pin the markup and the tokens; `pnpm check:layout --url <web dev server>` measures the geometry in a browser (it needs `agent-browser`; `--login <email>` with `CHECK_LAYOUT_PASSWORD` adds the signed-in pages). It is not part of CI.

1. **The footer sits at the bottom of a short page.** The arena's public shell (`apps/web/src/components/public-shell.tsx`, used by the `_public` layout and the 404) owns the one public footer (`components/public-footer.tsx`: the disclaimer, the AI disclosure and, with analytics, Cookie preferences). Inside `<main>`, the content is one `flex min-h-full flex-col` column: the routed page grows (`flex-1`) and the footer comes last, so on a short page (The rules, an empty leaderboard or studio) the footer's bottom is the scroller's bottom, and on a long page it follows the content. No `position: fixed` footer, no second scroller, and no `<footer>` in a route file or an arena tab: footer content goes into `PublicFooter`. `.cc-app` carries no bottom padding; the footer row's own padding ends the page. The CLI local lab (`components/chess/local-model-lab.tsx`) puts its own footer (the local-only note and its address) in the same column. The app shell (`_app`) has no footer: phones get the BottomNav, Cookie preferences (with analytics) sits in Settings.
2. **Full-bleed dividers span the viewport.** The arena header's rule (`.cc-header`), the footer's rule (`.cc-footer`), the app header's `<hr>`, the admin sub-nav and the setup banners reach from 0 to the viewport's right edge at every width, also past 1440px: the arena header's border sits on the full-width header and only its row (`.cc-header-row`) is capped; the footer's rule is full width and its text keeps the `.cc-app` column. On a page that scrolls, rules inside `<main>` meet its visible scrollbar. That is why no `<main>` (arena, app shell, local lab) reserves a scrollbar gutter: with classic scrollbars (Windows, Linux) a stable gutter is an empty 15px strip that every rule inside the scroller stops short of. The cost is that centred content moves by half a scrollbar when a page grows past the viewport on those platforms; overlays lock the document, not `<main>`.
3. **No surface ignores the theme.** The theme is the stored choice, else the OS, applied as the `.dark` class before first paint (`packages/config/src/theme-init.ts`); the CLI local lab has no toggle and so no stored choice, and follows the OS live (`apps/web/src/local.tsx`). Every surface uses the tokens in `packages/ui/src/styles/globals.css` and `dark:` variants, never a `prefers-color-scheme` query or a literal colour; a new colour becomes a token there. That includes the arena palette (`--cc-*`, light on `:root`, dark on `.dark`) and the dark arena's shadcn overrides (`.dark .cc-public-shell`). The deliberately fixed colours in `apps/web/src/index.css` (board squares and pieces, the hero board art, and the White/Black depictions: avatars, swatches, the evaluation bar and graph, remark bubbles, result marks) carry a `theme-exempt: <reason>` comment on their line, which G9 requires; the share image and video frames are drawn on a canvas and are not CSS. A model's legal-move lookup on the board (`.cc-lookup-*`: the looked-up square, a dot per target, a ring per capture) uses the `--cc-lookup-*` tokens, which carry one value in both themes because they sit on the fixed board: a dark mark with a light halo, so it reads on light and dark squares alike. A CSS `url(#id)` is an element reference, not a colour. Toasts are a popover surface: `globals.css` fills sileo's pill with `--popover`, writes the title in `--popover-foreground` and maps sileo's state colours to `--state-*`, `--destructive` and, for the action state, `--state-info` (dark `--primary` is a button fill, too dark for text on the dark popover); the Toaster gets no `theme` prop (sileo's themes invert the page). Text and state colours reach 4.5:1 on the surface they sit on in both themes.
4. **Every route renders inside a shell, the 404 included.** An unknown URL matches no layout, so `$lang`'s `notFoundComponent` (`PublicNotFoundPage`) wraps the not-found body in the public shell: header with language and theme controls, footer, scroller. The router's `defaultNotFoundComponent` (`NotFoundPage`) is the body alone, for a route that sets its own boundary inside a shell. A `notFound()` thrown by a route without its own `notFoundComponent` lands on the same public 404. Fixed chrome follows the shell it belongs to: the cookie banner (only with analytics) reserves room for the BottomNav only while one is mounted (`data-bottom-nav`).

## Layer scale

The app keeps the template's layer scale (`patterns/design-system.md` in the template repo). It is recorded here because the cookie banner once sat at `z-[60]`, above the overlays, and covered a row-actions menu opened near the bottom of `/admin/users`. The banner, the BottomNav and every portal sit on the root stacking context, so these numbers compete directly. That holds only while none of them has an ancestor that opens its own stacking context (`isolate`, a `z-*` on a positioned element, `transform`, `filter`, `backdrop-filter`, `opacity` below 1, `will-change`, `contain`), so fixed chrome mounts at the shell or root level. A portaled popup competes through its outermost part (Positioner, Backdrop/Overlay, Viewport):

| Layer | Who |
|---|---|
| `z-10`, `z-20` (and `-z-1`), small CSS values (the board's `.cc-*` cells and badges at 1–4) | Inside a component; never used to beat app chrome |
| `z-30` | Sticky page chrome |
| `z-40` | Non-modal fixed chrome over the page: the cookie banner. Below every overlay, so an open menu, select, popover, combobox, dialog, sheet, drawer or toast is never covered; below the BottomNav, which paints over the banner's bottom padding |
| `z-50` | The overlay layer: the `packages/ui` portals (dropdown menu, select, popover, dialog, alert dialog, sheet, drawer), the sileo toast viewport, the mobile BottomNav and the focused skip links |

Nothing goes above `z-50`. Utilities use only the steps above (`-z-1`, `z-10`, `z-20`, `z-30`, `z-40`, `z-50`): no arbitrary `z-[…]` / `z-(…)` values and no other numbers. Every overlay root carries an unconditional `z-50` (a responsive-only `md:z-50` leaves phones without a layer). A new banner, tray or floating button is `z-40` or lower and reserves its own space through the scroller's bottom padding, never the shell frame, as the banner does with `--consent-inset`.

What checks it:

- `apps/web/src/components/consent/consent-layers.test.tsx` is the safety net. It renders the banner and checks its layer against every portaled overlay in `packages/ui/src` (read from the components, so a new overlay is covered), the sileo toast viewport and the BottomNav, and that no overlay is lowered below `z-50` through the `className` it is given (in app code or a shared wrapper such as `CommandDialog`).
- `pnpm policy:checks` is a line grep for the obvious cases: an off-scale `z-…` utility in `apps/web/src` or `packages/ui/src` (markup, class strings, `@apply`).
- Neither catches: custom CSS classes and stylesheets (`.my-sheet { z-index: 30 }`, a `[data-slot=…]` rule, however its selector is spaced, nested `@media` blocks), CSS `z-index` declarations and inline `style` / `zIndex`, class names built at runtime (`` `z-${n}` ``) or held in a constant, layers set through pseudo-element or descendant variants (`before:`, `*:`, `[&…]:`, which the test skips), and an ancestor that opens its own stacking context. Those are review items; real hit-testing needs a browser.

## Shared components

The template's shared-component rules (template-ux T3), as they apply here. `packages/ui/src/components/*.test.tsx`, `packages/ui/src/hooks/use-scroll-edges.test.ts`, `apps/web/src/components/mode-toggle-menu.test.tsx` and `apps/web/src/lib/theme-contrast.test.ts` pin them.

- **Copyable values.** `CopyField` (one line) and `CodeSnippet` (a block) share one code size, `font-mono text-xs leading-5` (12px). The copy button sits in its own 44px column beside the text, never over it: `CopyField`'s border is on `copy-field-box` around the scroller, and `CodeSnippet`'s root is the bordered box with the `<pre>` and the button side by side (no `absolute`, no `pr-12`). A long value scrolls inside its box and fades at the edge that has more (`scroll-fade-x`). `CodeSnippet wrap` wraps long lines instead (`whitespace-pre-wrap [overflow-wrap:anywhere]`); use it for logs and tool output (the replay's tool details), never for commands or config, where a line break changes the meaning.
- **Scroll cue on selector rows.** `useScrollEdges` (`packages/ui/src/hooks/use-scroll-edges.ts`) sets `data-overflow-start` / `data-overflow-end` while content lies past that edge, re-measured on scroll and resize; the `scroll-fade-x` utility in `globals.css` fades that edge over 1.5rem with a mask (RTL-aware, no layout shift, no animation). `SelectorRow` uses it with `scroll-px-6`, and a focused item is scrolled into view clear of the fade (instant under reduced motion). The arena's own strips (`.cc-tabs`, `.cc-timeline`) are not `SelectorRow`s and do not get it.
- **Field outlines.** `--input` (input, textarea, select, checkbox, the Off switch track) is non-text UI and reaches 3:1 in both themes on `--background`, `--card`, `--popover`, `--muted`, the arena's `--cc-bg`, `--cc-surface` and `--cc-raised`, and the dark arena's `--muted`. `--border` stays decorative. The Off switch track is the opaque `bg-input`, never a translucent tint. The arena's own form CSS (`.cc-form-grid`, `.cc-create-body` in `index.css`) draws its fields with `--cc-line-strong`, not `--input`. Because `--input` is a strong colour, a fill made from it must still carry muted text: a hovered trigger stays at `dark:hover:bg-input/35` or lighter, and a search field in a menu or picker (`CommandInput`, the async comboboxes) uses an opaque `bg-muted` fill with `placeholder:text-muted-foreground` (Tailwind's default placeholder is the text colour at 50%). Light `--muted-foreground` is `oklch(0.54 …)` so it reaches 4.5:1 on `--muted`. `apps/web/src/lib/theme-contrast.test.ts` scans every `hover:bg-input/NN` for 4.5:1.
- **Toasts.** The `toast.*` facade (`packages/ui/src/components/sileo.tsx`) gives each toast its own id, so two toasts stack instead of one replacing the other (sileo's default id is shared). sileo draws the pill in a fixed 350px SVG, so `globals.css` caps the header row and ellipsises the title, which keeps the icon inside the pill; a message that would be cut off is also put in the description, which sileo expands under the pill in `--popover-foreground`. The facade measures the title at its real font and root size (`titleOverflowsPill`), because a short message of wide glyphs, or any message at a larger root font size, can overflow while a character count says it fits; where nothing can be measured it falls back to a 40-character rule. The action button's text reaches 4.5:1 on its 8% and 14% tints.
- **Menus.** Dropdown menus (`DropdownMenuContent` and its sub content) are opaque `bg-popover`, with no translucency or blur, so a banner behind never tints them. A menu that picks the current choice uses radio items: the header theme menu (`apps/web/src/components/mode-toggle-menu.tsx`) is a `DropdownMenuRadioGroup` bound to the stored theme (none stored counts as System), so the choice in force shows as checked (`menuitemradio`, `aria-checked`).

## Form surfaces

From the template (`patterns/design-system.md` § Form surfaces in the template repo). Where a create or edit form lives is decided by its length, not by habit. A tall dialog that scrolls inside itself hides the action button and the errors below the fold, and on a phone it is a scroller inside a scroller.

- **A dialog is for confirmations and short forms only:** about six controls or fewer, and it must fit **without inner scrolling** at 1280×800 and 390×844. `pnpm check:dialogs` opens every dialog the app lists and fails one that scrolls (§ Dialog fit check).
- **Anything longer becomes a full page or a wide side sheet,** using the whole width: sections with headings, two columns of fields from 1024px (`lg:`), one column on phones. A page (`FormPage`, its own route) is deep-linkable and the default for creating something; a wide side sheet (`<SheetContent size="wide">`) is for working without leaving the page behind it. Studio's Create match is the app's wide side sheet (`apps/web/src/components/chess/create-match-dialog.tsx`; its arena look is the `.cc-create-*` CSS in `apps/web/src/index.css`, which sets its own width of `min(64rem, 100%)` at every breakpoint).
- **The quick path first.** Up front go the few fields most people must decide, with safe defaults pre-filled; expert fields go under collapsed sections named by topic, each summarising its current values while closed. Anything the app can work out is derived, not asked.
- **No raw configuration.** Key-value pairs use `KeyValueEditor`, never a JSON textarea. Every enum and option has a human label (`SelectField` `options`).
- **Sticky header and action bar** on every dialog, sheet and long page: the title and close button never scroll away, and the primary action is always on screen.
- **Errors inline, focus on the first invalid field** (§ Errors next to the field), never only at the bottom or in a toast.

The parts (`packages/ui`):

| Surface | Component |
|---|---|
| Short create form, confirmation | `Dialog`: the popup is capped at the visible viewport (safe areas included) and does not scroll; its body (`data-slot="dialog-body"`, styled through `bodyClassName`, not `className`) does, with `DialogHeader` stuck to its top, `DialogFooter` to its bottom and the close button pinned to the popup. `AlertDialog`: the popup is the scroller, with the same sticky header and footer. |
| Edit in context, long form beside its page | `Sheet` + `SheetHeader` + `SheetBody` (the one scroller) + `SheetFooter` (pinned); `size="wide"` for long forms (full width on phones, 48rem, 64rem from `xl:`). |
| Long create form | `FormPage` (`components/form-page.tsx`: header, `FormSection`s, `AdvancedSection`s, sticky `FormActionBar`). A layout with a sticky sub-nav sets `--page-sticky-top` (the admin layout does). |
| Numbers in a range | `RangeField` (`components/range-field.tsx`): slider plus typed input, snap stops, units (`lib/range-scale.ts`), a marked default and a dynamic limit; the field never holds a value the UI rejects. |
| Key-value pairs | `KeyValueEditor` (`components/key-value-editor.tsx`): rows plus a `.env` text mode (`lib/dotenv.ts`), masked secrets; `hasKeyValueErrors` gates submit. |

Sticky headers and footers carry the edge padding themselves: never give them negative margins (a sticky box cannot leave its container, so it would be pushed over the content). An arena dialog (`.cc-dialog-content`) paints its sticky header and footer in the popup's own `--cc-raised`, so they match the popup. `RangeField` and `KeyValueEditor` labels come from `useRangeFieldLabels()` / `useKeyValueEditorLabels()` (`apps/web/src/hooks/use-form-field-labels.ts`, strings under `common:forms`); `@cockpit-chess/ui` ships no strings.

### Select fields

A field-bound select uses `SelectField` (`packages/ui/src/components/text-field.tsx`) with its choices as data, `options: { value, label }[]`, never `<SelectItem>` children. Base UI's closed select prints the chosen option's label only when the root gets an `items` map; without it the trigger shows the raw value (`user` instead of "User"). `SelectField` passes `options` as that map and renders the items from the same list (`text-field.test.tsx` pins it). Every `label` is translated; a raw `<Select>` outside `SelectField` passes `items` to its root for the same reason.

### Errors next to the field

Validation errors appear inline, under the field they belong to (`TextField`, `SelectField`, `RangeField` and `KeyValueEditor` render them and set `aria-invalid`). A failed submit moves focus to the first invalid field: give the `<form>` a ref and `noValidate`, set `onSubmitInvalid: () => focusFirstInvalidField(formRef.current)` in `useForm` (`packages/ui/src/lib/focus-first-invalid.ts`; it opens a collapsed `AdvancedSection` around the field first), and leave the submit button enabled while the form is invalid (disable it only while submitting). A string schema's `.min(1)` reads as "required" (`apps/web/src/i18n/zod.ts`).

## Route pending states

On a hard refresh of a signed-in page, what paints first must already be the app: the same header and bottom nav as the loaded page, in the stored theme, with only the **content area** as a skeleton shaped like that page. Nothing outside the content moves when the page arrives. A blank frame or a bare spinner before the shell pops in is the bug this section prevents.

The signed-in layout `$lang/_app` is `ssr: false`, so the server renders that route's **pending component**, and the client keeps it until the layout can mount (hydration, the auth check). So:

- `_app`'s `pendingComponent` renders the shell's own frame (`AppShellFrame` in `apps/web/src/routes/$lang/_app/route.tsx`, the same function the layout renders) around `RouteContentSkeleton`. `apps/web/src/components/public-shell.test.tsx` pins that the pending frame and the loaded frame are the same markup outside `<main>`.
- Every pending boundary below it (the router's `defaultPendingComponent`, the forced-2FA gate's settings load in `_auth.tsx`) renders `RouteContentSkeleton` (`apps/web/src/components/route-content-skeleton.tsx`) alone, inside the shell already on screen. `Loader` is left only for the i18n bootstrap (`I18nReady`).
- Each route declares its shape in `staticData` (`apps/web/src/lib/pending-layout.ts`): `pendingShape` (`"list"`, `"detail"`, `"form"`, `"dashboard"`), `pendingWidth` (the `PageShell` width) and, on a layout route that draws chrome around its children, `pendingFrame` (`"admin"`: the admin sub-nav; `"settings"`: the settings title and side nav). A new signed-in route sets its `staticData`; a new layout with its own chrome adds a `PendingFrame` and draws it in `route-content-skeleton.tsx`.

- The first paint waits for the whole frame: `_app`'s `head` adds `<link rel="expect" href="#app-shell-end" blocking="render">`, so a browser that has parsed only part of the document (the HTML arrives in pieces on a slow network) does not paint a header without the scroller and bottom nav. Browsers without `rel="expect"` ignore it.
- Content that appears above a page after it loads moves the page. The admin layout loads the app settings with the route (`loader`), so the 2FA nudge (`TwoFactorNudge`) arrives with the page instead of pushing it down.

The arena (`_public`) is server-rendered and has no pending shell of its own.

## Browser checks

Two real-browser checks from the template, beside `pnpm check:layout` (§ Shell rules). `scripts/check-dialogs.ts`, `scripts/check-shell-loading.ts` and `scripts/browser-check-lib.ts` stay identical to the template's; `scripts/browser-checks.config.ts` is this app's: it has no mock mode (`MOCK_SERVER = false`), so both need the running stack, `--url`, and an admin account given like `check:layout`'s (`--login <email>`, the password in `CHECK_LAYOUT_PASSWORD`, never on the command line). `--no-sandbox` for Ubuntu 23.10+ Chromium. They need agent-browser and are not part of CI; run them after touching a dialog, the shell, a layout route or a pending state. The judging logic has unit tests (`pnpm check:dialogs:test`, `pnpm check:shell-loading:test`, in `pnpm verify:tooling`).

### Dialog fit check

`pnpm check:dialogs` enforces § Form surfaces. It opens every dialog in `DIALOGS` at 1280×800 and 390×844 (`--only "<name>"` runs one) and fails when the popup or anything inside it scrolls vertically, when a sticky header or action bar covers content, when the popup reaches outside the viewport, or when the dialog does not open. Add one entry per dialog an admin can open without changing data, confirmations included; a dialog that cannot fit becomes a page or a wide side sheet and leaves the list (there is no exemption field). Sheets are not measured. A `waitFor` step waits for a selector between steps, or last, for a dialog that is still loading when it opens (Export video measures its options after the codec probe). Fixtures the list needs on the stack: one published game, one API key, and a second user named "Dialog Check Fixture" (Revoke API key and Delete user only open their confirmations).

### Shell loading check

`pnpm check:shell-loading` enforces § Route pending states. An init script records, on every animation frame from the start of the document, the boxes of the header (`[data-app-header]`), the bottom nav (`[data-bottom-nav]`) and `<main>`, the theme class and whether the content skeleton (`[data-route-skeleton]`) shows, plus layout shifts. At 1280×800 and 390×844, stored theme dark and OS light, it hard-reloads the pages in `SHELL_PAGES` with the network (150ms, 4 Mbit/s) and CPU (4×) throttled, and fails when the first painted frame has no header, `<main>` or bottom nav, or is not the content skeleton; when a later frame loses the header; when the header, the bottom nav or the top of `<main>` moves by more than 1px before the page has loaded; when a frame is in the other theme; or when cumulative layout shift exceeds 0.05. Each page's `ready` selector exists only once its real content has loaded.
