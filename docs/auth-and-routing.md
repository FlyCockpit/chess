# Auth and routing

Session guards and identity rules for the web app (`apps/web`). The template's `patterns/auth-and-routing.md` has the full routing guide; this file records how this app applies its identity rules.

## Query cache follows identity

The TanStack Query cache, module state and every in-flight request callback belong to one identity: the one the document was used by. `apps/web/src/lib/document-identity.ts` keeps that identity at module scope for the whole life of the document (never in a component, which a remount would make forget). When a confirmed identity differs from it, the document is replaced with a full load. A page load is asynchronous, so every replacement first quarantines the document synchronously: the page is hidden (`display: none !important` on the root, which no descendant can undo) and the QueryClient sealed (emptied, and anything a late callback adds is removed again), so nothing of the previous identity stays on screen while the new page loads.

| Transition | What happens |
|---|---|
| Explicit sign-out (the account menu, `user-menu-content.tsx`) | `signOutAndLeave()` (`apps/web/src/lib/explicit-sign-out.ts`): marks the sign-out, then on success `leaveDocument()` to login, a fresh document with an empty cache. A failure (returned or thrown) undoes the mark; add any new sign-out button through it. |
| Signed out elsewhere (another tab, expiry, revocation) | The document reloads in place; the guards send the visitor to login. |
| Another account (same tab or another tab) | The document reloads in place; the guards admit the new account and its queries load fresh. |
| Anonymous → signed in | Local sign-in keeps its client-side navigate. On login/signup/forgot/reset, a peer sign-in replaces the document unless that user was already confirmed locally (`markAnonymousOnlyRoute`). |
| `pending` / `error` | Never acted on: a flaky session check must not reload a signed-in page. |
| Signed out elsewhere, or another account, while a page that holds no account data is open (the hosted Lab tab) | No reload: the account state is dropped in place, and the full load waits for the first navigation to any other page (see below). |

The following observers feed it, and none can be skipped:

- **Every session guard** (`_auth`, `admin`, `login`, `signup`, `forgot-password`, `reset-password`) calls `resolveRouteSession()` (`apps/web/src/lib/route-session.ts`): `getRouteSession()`, then the identity check. A different identity replaces the document and the guard never settles, so no page under it renders the previous identity's cached data. An answer to a probe that started before a newer identity was recorded (a hover preload sent before this tab signed in) is out of date: the guard probes again and uses only the fresh answer. `pnpm policy:checks` rejects any route-file reference to `getRouteSession` or `@/server/auth-session`.
- **The watcher**, `useReloadOnIdentityChange()`, for a change while a page is open. The `_app` shell frame runs it eagerly (`AppShellFrame` in `routes/$lang/_app/route.tsx`, shared by the pending shell and the loaded one), so it is connected before the shell shows the account or any guarded page renders. The hosted root also mounts it through `IdentityBoundary` (`apps/web/src/components/identity-boundary.tsx`), loaded lazily on the first account-aware page (any `_app` page, the public Studio tab, or once the identity is unverified, see below; `useIdentityBoundaryEnabled`) and kept mounted across public navigation, so it also covers the public pages; its loader (`identity-boundary-loader.tsx`) contains a failed chunk load (nothing renders, the page stays, the identity stays unverified) and retries when the tab is back in front or online. Both share the document's baseline and its one reload. The Studio tab is private UI that no guard covers, so it shows and fetches its admin data only once the document has recorded the signed-in account (by a guard or the watcher) and the watcher is connected (`useDocumentAdmits`); until then it shows its skeleton, never a cache the previous account filled before anything was watching. It runs in a layout effect, before a frame pairs the new chrome with the old data. It also connects the open tabs: Better Auth tells other tabs about a sign-out but not a sign-in, so each newly confirmed identity (seen by the watcher or by any guard) is announced on the document's `BroadcastChannel`, the auth client announces every session change made in the tab (`$sessionSignal`: sign-in, sign-up, 2FA) before the flow navigates, and SSO returns through the login guard. Confirmed peer messages carry `{ kind: "identity", id }`: matching identities cost no request; conflicting identities and session-change hints share one check, including any native refresh already in flight. Unversioned messages never establish identity without a server answer.
- **The public document verifier** opens the existing document peer channel in `watchDocumentRestore()`, including fresh public and 404 loads, without loading Better Auth or probing a session routinely. When a peer event arrives without a watcher, it lazily loads the shared verifier, updates the same session atom, and reconciles the document identity through the existing coordinator and retry budget. A retained public retry still reconciles if an app watcher mounted meanwhile. Existing public hint listeners refresh promptly; the retained lazy root watcher remains the sole root watcher. The Lab keeps its account-free discard behavior.
- **The global error toasts** (`apps/web/src/router.tsx`): before any toast opt-out, a query rejected with 401 asks Better Auth to check the session (one check in flight at a time) instead of toasting; a mutation still toasts. Hidden admin procedures (`adminOr404Procedure`) answer a lost session with 404 by design, so while the document believes a user is signed in, a 404 (query or mutation) checks the session too, and toasts as before. Better Auth's own requests feed the same check: the auth client's `onError` turns a 401 on an account action (Settings' profile save, `updateUser`) into a session check while signed in (`reportAuthErrorStatus`; a wrong password on the sign-in page is a 401 too and checks nothing). Nothing toasts once the document is being replaced.

A decoded private 401 (including individual batch items) requests verification before Query retries or final error callbacks. The first rejection advances the verification generation so a pending pre-event A answer cannot certify it. Identical interceptor/cache error notifications and concurrent rejection bursts share one post-event check. Only that reconciliation sends `disableCookieCache=true`; successful authoritative answers clear it, and failures retain it through the existing Retry-After/backoff. The server's global 60-second cookie cache remains unchanged. A valid fresh same-account answer keeps the document; 403 remains an ordinary permission error. Hidden-admin 404 and Better Auth account-action 401 handling remain in place. Ordinary network/server query failures retain the normal client retry budget.

Every error boundary's Try again uses router invalidation with `forcePending: true`, including generic render errors, so guarded ancestors finish before a successful private child can recover with old session context. It does not reset the boundary ahead of the guard. Real mounted router regressions cover both child and parent render failures. The document title contains only the translated brand and needs no private-title mask.

**Neutral chrome until the identity is confirmed.** Better Auth's atom can hold the previous account's session while nothing has checked it yet. Two masks make `useAuthSession()` report `pending` whatever the atom holds, so the account menu, nav and every other session reader show their pending state instead of that account:

- The `_app` shell's pending state (`AppShellPending`) paints before any guard has admitted anyone; it renders under `SessionUnconfirmed` (`apps/web/src/lib/session-unconfirmed.ts`).
- A peer tab's announcement or a 401 that arrives while no watcher is connected marks the document's identity unverified (`lib/document-identity.ts`, generation-counted). It stays unverified, on every page, until a fresh check confirms this document's identity or replaces the document: a guard's server answer (`resolveRouteSession`), or a refetch a watcher starts itself when it connects (retried on focus, visibility and reconnect while unverified; one superseded by another fetch still running is followed up, at most 3 times 250 ms apart; all dropped when the watcher unmounts). An answer asked for before a newer invalidation never counts, and only a settled, successful answer does (`readSessionIdentity`: a 503 with the previous account retained confirms nothing). A public page has no `_app` watcher, so an unverified identity also loads the root's lazy watcher (`useIdentityBoundaryEnabled`): the mask never waits for a watcher that would not load. The watchers read the session unmasked (`useAuthSession({ unmasked: true })`), so they still see the answer that settles it.

Pages without a watcher subscribe through `onPeerSessionChange`; an unverified identity activates the root watcher. Anonymous-only pages mark their current pathname with `markAnonymousOnlyRoute`, so a peer sign-in replaces the form before the new account can appear beside it.

**Pages that hold no account data** (`apps/web/src/lib/account-free-pages.ts`): an explicit allowlist, today the arena home `/$lang/` on its public tabs (arena, leaderboard, lab, methodology; never Studio). They render only public procedures (`chess.list`, `chess.get`, `chess.leaderboard`: the same answer for every visitor), the session-cookie hint and device-local state such as the Lab's imported archive. When a different identity is confirmed while one is open (and no navigation to another page is in flight), `replaceDocument()` does not reload: it drops every mutation and every query no mounted component uses (whatever earlier pages cached: Studio's lists, settings), and refreshes what is on screen (public, the header's session hint included), so the visitor's local work survives. The document stays replaced: private UI never admits anyone on it again, and the router calls it again before every later navigation (`replaceDocumentBeforeNavigation` on `onBeforeNavigate`), so the first one to a page that is not on the list gets the full load, at the destination's URL, before that page renders. The browser history writes that URL a microtask after the event, so the hook flushes it first; reloading before that would load the page being left (the Lab, without its archive) instead. A late callback that writes the old identity's data back can only reach a cache that no allowlisted page reads. Add a page to the list only if nothing on it reads account data.

The router also covers the back/forward cache: a document that ever held a signed-in user's state (recorded by a guard or the watcher, or a signed-in session seen by `useAuthSession`, so a fresh `verify-email` page counts too) is hidden as it enters the cache and reloaded when restored, so Back never shows a frozen page nobody re-checked. Anonymous pages are cached as usual.

Persisted client storage holds no private data: `localStorage` keeps only device choices (locale, theme, consent) and Better Auth's cross-tab session message (`better-auth.message`: an event name such as `signout`, a client id and a timestamp), and `sessionStorage` the stale-build recovery cooldown and the router's scroll restoration (`tsr-scroll-restoration-v1_3`: scroll offsets per history entry). The CLI local lab (`apps/web/src/local.tsx`) is a separate document with its own QueryClient and no Better Auth session, so none of this applies there. A new store of private data in browser storage needs its own identity scoping or clearing.

Why a full load, not `queryClient.clear()` or a fresh `QueryClient`: clearing the cache while observers are mounted cancels their fetches silently and can leave the page stuck on a skeleton, `resetQueries()` refetches active queries as the wrong identity, and neither stops an in-flight mutation whose late `onSuccess` writes the old identity's data back. A swapped client still leaves module state behind. A full load drops all of it, and a late callback can only write into the document being discarded. The one exception is the allowlist above: a page that renders no account data has nothing of the previous identity to show, its mounted queries are public, and the deferred full load still runs before any page that could read the leftovers renders.

Cookie requests carry `X-Expected-User` from the document baseline: oRPC and OpenRouter connect, plus Better Auth except get-session/sign-out. Hono compares the raw cookie owner before ban filtering on `/rpc`, `/api-reference`, and `/api/openrouter`; Better Auth compares in `hooks.before`, sharing its session lookup. A different cookie owner returns 409 `{ code: "IDENTITY_CHANGED" }`; lookup failures return 503. This consistency check never grants access. The client intercepts the answer before success/error callbacks, quarantines or discards the old document, and leaves the old request unsettled. Other late responses are suppressed too. CORS permits the header and exposes `Retry-After` (already exposed by this app).

A session availability failure (429, server failure, offline) shows **Account unavailable**, Retry and Sign out. `session-retry.ts` coordinates one document-level check with 2→60 second backoff, Retry-After, and hidden/offline suspension. Native Better Auth refreshes share the check and cooldown; its duplicate focus refresh is disabled in favor of the coordinator. Retained account data never counts as a new confirmation. Failed offline sign-out explicitly says the session is still open, in both shipped locales.

## Password pepper

Password hashes use Better-Auth's scrypt, sealed with AES-256-GCM under a key derived from `BETTER_AUTH_SECRET` with HKDF-SHA256. A database dump, backup, or read-only SQL injection no longer yields crackable hashes without the server secret. A full server compromise with that secret is outside this protection.

Stored format: `pw1:<16-hex key fingerprint>:<base64url(nonce || ciphertext || tag)>`. The fingerprint identifies the key without revealing it. The authenticated additional data (AAD) is `password-v1`. Better-Auth's password hooks receive no user id, so values are not bound to their row. A database writer can still swap two accounts' values.

The server seals legacy unsealed hashes and authenticates every sealed value at startup, in one transaction under an advisory lock, before listening. Sign-in never accepts unsealed hashes. Corrupt values produce a startup warning with a count and the recovery command; startup still succeeds when no unknown keys remain. `pnpm doctor:app` reports fingerprints, counts, and structurally invalid envelopes without changing data. It does not receive the key in its database probe; cryptographic authenticity is checked at server start.

To rotate the secret:

1. Stop every server/replica. Set `BETTER_AUTH_SECRET_PREVIOUS=<old>` and `BETTER_AUTH_SECRET=<new>` for EVERY server/replica at once, then restart them all. Both secrets must be strong, at least 32 characters, and different. Never run replicas with different `BETTER_AUTH_SECRET` configurations side by side: an old-config replica can neither verify re-wrapped hashes nor write current-key ones.
2. Check that the log `password pepper: re-wrapped … none remain under the previous key … BETTER_AUTH_SECRET_PREVIOUS can now be removed` or `pnpm doctor:app` shows 0 remaining under the previous key. Resolve doctor's invalid-envelope warnings before relying on its fingerprint inventory. If hashes remain, keep PREVIOUS set and restart all servers again. If they are corrupt, use the recovery command below.
3. Only after 0 remain, remove `BETTER_AUTH_SECRET_PREVIOUS` everywhere and restart all servers again.

Rotating `BETTER_AUTH_SECRET` still signs out every browser (cookie) session and makes existing TOTP enrolments undecryptable, as before. It does not end CLI device-flow sessions or API keys: those are checked against the database, not the secret. If you rotate because of a suspected leak, also revoke those credentials: delete the user's API keys, and delete all of that user's sessions with Better Auth's admin `revoke-user-sessions` (it deletes every session row of the user, including the CLI's). "Sign out other devices" alone lists at most 100 sessions, so it can miss some. The previous key applies only to the password pepper; it does not change any of this.

A `PasswordPepperKeyError` refuses startup when stored values name an unconfigured key. Restore the secret used to write them, as `BETTER_AUTH_SECRET` or as `BETTER_AUTH_SECRET_PREVIOUS` during rotation. The message names fingerprints, never secrets.

If the key is lost, or values are corrupt or malformed, the owner stops all servers and runs recovery as a one-shot from a checkout with the validated server environment and database access. It needs no listening server:

```bash
pnpm auth:pepper:reset-unusable                     # dry run: count and affected user ids
pnpm auth:pepper:reset-unusable --confirm <count>   # exact count from the dry run
```

For production or any non-local database, add `--allow-non-local` to both commands, with all servers stopped. The command uses the same local database guard as maintenance scripts by default. It replaces only unusable password values with random passwords nobody knows, sealed under the current key. It keeps credential rows, legacy hashes, and authentic current/previous values. Start the server, then tell the listed users to use the normal forgot-password email flow. SMTP must work for that flow.

**Backups:** `BETTER_AUTH_SECRET` also protects passwords. Back it up separately from the database and retain keys needed by older backups. A lost key requires the recovery procedure above for affected passwords. See [backup-and-restore.md](./backup-restore.md).

## Guards wait for the shell to hydrate

`_app` is `ssr: false`, so on a hard refresh the server sends its pending shell for the URL (header, nav, a content skeleton shaped by the URL). React hydrates each Suspense boundary in a later, low-priority pass, but the router runs the guards as soon as the outer tree commits. The router's stores hand React their current state as the "server snapshot", so a redirect that lands before the shell hydrated makes React hydrate the shell for the new URL against the old URL's HTML: React error #418 (a signed-out cold load of `/settings`, a signed-in one of `/signup`).

- `resolveRouteSession()` waits for `appShellHydrated()` (`apps/web/src/lib/app-shell-hydration.ts`) in parallel with its first probe, and a failed probe also waits before it reaches the router. So every guard decides (redirect, not-found, error) only after the shell hydrated. A re-probe for an out-of-date answer (§ Query cache follows identity) does not wait again.
- The shell frame (`AppShellFrame` in `routes/$lang/_app/route.tsx`, the pending shell and the loaded one) carries `data-app-shell` and reports from its mount effect. The wait applies only while a server-rendered shell is in the document and has not reported: never on the server, never on a client navigation from a public page. It is capped at 5 s.
- Only the `_app` shell needs this. The public (arena) shell's `beforeLoad` only seeds the session hint and never redirects; `/` and `/$lang/dashboard` redirect on the server, before any HTML is sent.
- A new guard uses `resolveRouteSession()` like the others. A guard that changes the URL some other way during the first load must await `appShellHydrated()` first.

## Session state after the first load

`useAuthSession()` reports `pending` only for the first load of a document, apart from the two identity masks (the pending `_app` shell, an unverified identity: § Query cache follows identity). Once Better Auth's session atom has settled `anonymous`, it stays `anonymous` while Better Auth refetches (window focus, a peer tab's announcement) and through a failed refetch; a confirmed session replaces it as usual. Better Auth marks every request of an empty session `isPending` again, which looks the same as the first load, so without this memory every refocus showed the auth pages' skeleton and unmounted the sign-in form with what the visitor had typed. The memory lives in `hooks/use-auth-session.ts` for the whole document, because the atom is shared. It is not the document identity's baseline: that is recorded only by the guards and the watcher, and says whose cached data the document holds. `components/auth/auth-form-refocus.test.tsx` pins it.

## One h1 per page

Every auth page (sign-in, sign-up, forgot and reset password, verify email, the two-factor challenge, "unable to connect") is an `AuthCard` (`apps/web/src/components/auth/auth-screen.tsx`), and its title is the page's one `<h1>`. The forced-2FA takeover (`_auth.tsx`) and the CLI device page (`_auth/device.tsx`) title their card with the h1 the same way. Settings has one h1, the layout's title; its pages title sections with card titles. The 404's title is its one h1 in either shell. No shell chrome has a heading, and nothing fakes one with `role="heading"` (`components/auth/auth-page-headings.test.tsx`, `components/not-found-page-shells.test.tsx`, `components/settings-headings.test.tsx`).

## Admin invites

An admin invite sends one mail: a one-time set-password link (a `reset-password:` verification row, 7 days, `packages/api/src/lib/set-password-link.ts`), never a password, and no separate verification mail. Spending any reset token (the invite link or Forgot password) signs out every session, revokes API keys, device-flow sessions and device codes, and deletes the user's other reset links (`packages/auth/src/credential-revocation.ts`). It verifies the email only when that very link was mailed (see below). The admin picks the invitee's email language on the invite form; it is saved as `User.locale` in the first insert, so the set-password page and every later mail use it. When the mail can't be sent, the admin sees the link once. A resend re-checks that the invite is still pending inside its minting transaction, under a per-user lock that a finishing reset also takes; the reset deletes every other reset link of the user, so an invitee who completes setup during a resend never keeps a fresh link. Invite and resend each send mail, so both have fail-closed procedure budgets (30 per admin per hour, shared; 5 resends per invitee per hour). Archive acts at once and offers Undo in its toast.

**Only mailbox proof verifies an address** (`packages/auth/src/password-reset-links.ts`). After a reset or invite mail is accepted, `recordResetLinkMailed` writes a `reset-password-mailed:<sha256(token)>` verification row (the user id and the address, expiring with the link; no schema change), in one transaction under the set-password-link lock that checks the link still exists. The selective reset adapter consumes that proof, marks the email verified only while it is still the address the link went to, and deletes competing reset links in the same transaction as token consumption, session deletion and the password write. A password/commit failure rolls all those decisions back, so the same link can be retried; independent pre-sweep revocations may already have committed. A link the admin was shown (the mail was not sent) sets the password and verifies nothing: at first sign-in `requireEmailVerification` refuses, Better-Auth mails a verification link (`sendOnSignIn`) and the login form says so; until then the user is still a pending invite, so **Resend invite** keeps working and its mailed link verifies when spent. A `/reset-password` before-hook (`isResetLinkRedeemable`) lets a mailed link through in every state, and a shown link only while the user is still a pending invite (read under the set-password-link lock); otherwise it deletes the link and answers Better-Auth's own `INVALID_TOKEN`, the same as an expired link. Every verifying user write (including `/verify-email`) and noncredential IdP account insertion serializes on password-write → cli-credentials → set-password-link, on one client in a short transaction (`packages/auth/src/credential-setup-adapter.ts`). Verifying updates require one exact scalar, case-sensitive immutable id/email selector in both update methods; broad or insensitive selectors fail before lookup or checkout. The activation write and reset-link retirement commit together. The committed database after-hooks (`account-activation.ts`) only retry defensive link cleanup; they never establish mailbox proof or clear a password. Better-Auth user updates may not change `email` (`EMAIL_CHANGE_UNSUPPORTED`; reset links carry only the user id, and this app has no email-change feature) and `/admin/update-user` may not set `emailVerified` (`EMAIL_VERIFICATION_BY_MAIL_ONLY`; `packages/auth/src/email-change-policy.ts`). `/admin/create-user` runs only under the server's `admin-invite` grant (`users.invite`); an admin calling it over HTTP gets 403 `ADMIN_CREATE_USER_UNSUPPORTED`, and a user is created verified only on an IdP sign-in (`/callback/*`, `/sign-in/social`, whose `email_verified` claim this app trusts) (`refuseUnprovedUserCreation`, `packages/auth/src/user-creation-policy.ts`). The `SETUP_KEY` first-admin claim writes its verified admin through Prisma on purpose (the operator holds a deploy secret and types the address). Mailed-record and minting transactions take only the set-password-link lock in a lock slot. Activation takes all three locks on one transaction/client, in the order above; reset admission reuses its bound client under the existing outer password-write lock. Global Better Auth adapter transactions stay off so signup locale reads and SMTP remain outside a transaction. `pnpm runtime:test-operations` proves the invite races on real Postgres.

Authorized IdP insertion captures pending status **before** creating the noncredential account: unverified, exactly one credential account, and no live session. A fresh account with zero credentials is not a pending invite. For a pending invite, `sso-invite-activation.ts` clears any earlier shown-link password and revokes API keys, device codes, all owned and impersonated sessions, pending 2FA challenges and trusted-device proofs inside that same activation transaction. A second sweep catches rows inserted while the clearing write was uncommitted, before Better Auth can create the legitimate IdP session. Failed insertion/commit rolls back the link and clearing; a failed final sweep fails linking before a new session, keeping the committed password cleared. Existing fingerprint/challenge fences reject delayed old-password proof. Active accounts retain their passwords and sessions; fresh SSO signup remains supported under existing signup rules. Better Auth's pinned default `requireLocalEmailVerified=true` still denies implicit linking to an unverified local user. No trusted-provider, public-signup or FORCE_SSO policy changes make this internal activation seam reachable.

The allocator reserves both password-write slots before checkout (pool minimum 3). Nested activation/reset borrowers queue FIFO within that reservation; borrower lifetime stays charged after the parent exits, released capacity promotes local waiters, expired inherited reservations/tickets fail closed, and late-admitted descendants refund invalid idle spares once. A standalone activation reserves one slot and opens one client for all three locks. Queued Better Auth after-hooks run only after the reset transaction slot releases; per-request adapter transaction metadata suppresses those hooks on rollback without changing nontransactional signup behavior.

`cockpit-chess login` redemption (`POST /api/auth/device/token`) and every CLI-credential revocation serialize on one per-user advisory lock (`packages/auth/src/device-redemption-lock.ts`). A login caught mid-way by a password reset either loses its session to the revocation or finds its code gone. A device-flow session minted without the lock is refused, a busy lock answers `slow_down`, and `DATABASE_POOL_MAX` must be at least 3 (lock transactions take at most the pool minus one connection, and a password write holds two: `packages/auth/src/lock-slots.ts`). Creating an API key (`cliAccess.apiKeys.create`) takes the same lock and re-checks, inside it, that the session that asked still exists and has not expired; a session already deleted by a reset (or answered from the 60 s cookie cache) gets 401 and no key. Browser device approval now takes the same credential lock and re-checks the live authorizing session row before the original plugin handler. API-key minting also re-checks after insertion and discards its own key if the session disappeared; existing authority error codes stay unchanged. `pnpm runtime:test-operations` proves the race on real Postgres.

**A password reset ends every session, including a sign-in still in flight.** Better-Auth's `/sign-in/email` reads the stored hash, spends a deliberately slow hash check, and only then inserts the session, so a reset can complete in between. `POST /api/auth/sign-in/email` therefore runs inside a credential fence (`packages/auth/src/password-sign-in-fence.ts`, mounted in `apps/server/src/index.ts`): it fingerprints the credential hash before Better-Auth reads it and compares again once the session is committed. A changed credential means the session is refused or deleted and the answer is the ordinary wrong-password 401, with no cookies. The fence reads the credential only for a body Better-Auth would check (a valid email and a password), with one query that costs the same for an existing and a missing account, and it reads the body exactly as Better-Auth does (media type case-insensitive, a repeated form field keeps its last value). A two-factor challenge opened by the password step stores that fingerprint next to it, and the code step (`/two-factor/verify-*`) mints a session only while it still matches. The reset's revocation deletes every session (not only device-flow ones) and every pending `2fa-` challenge once more after the new hash is written, which covers a sign-in that lands between Better-Auth's own session delete and its password write. A password change with "sign out other devices" deletes every other session the same way and keeps the one it issued.

The same session-create hooks hold every other session Better-Auth mints to one rule, checked before the insert and again after it (a failed re-check deletes the row and fails the request, so no cookie is set). A session minted for a request that is already signed in (two-factor enable, disable and enrolment, impersonation) needs that parent session row to still exist: a reset deletes every session, so a rotation racing a reset either finds its parent gone or is deleted by the revocation. Besides the fenced paths (`/sign-in/email`, the two-factor code step, `/device/token`, `/change-password`), only an SSO callback (`/callback/*`, `/sign-in/social`) mints a session without a parent; any other session is refused.

Password writes for one user happen one at a time (`packages/auth/src/password-write-lock.ts`). `apps/server` runs `POST /api/auth/change-password`, `/reset-password` and `/admin/set-user-password` holding the user's `password-write:<userId>` advisory lock across the whole Better-Auth handler (the user comes from the session, the reset token's verification row, or the body). A change re-checks inside the lock that its session still exists, so one that waited behind a reset answers 401 and writes nothing; a reset that waits behind a change runs after it, so the reset's password is the last write and its revocation deletes the change's session. A write waits up to 10 s in total (one deadline covers the wait for a lock slot and the polling for the lock; a waiter past it leaves the slot queue) and then answers 503 `PASSWORD_WRITE_BUSY`. A password write without the lock (or after it lapsed) is refused by the account hooks, and so is the session a change mints. The lock stops counting as held 5 s before its 30 s transaction timeout. Because Better-Auth's UPDATE runs on another pooled connection after that check, the account after-hooks confirm the lock once the write has committed: the lock transaction must still answer (an open transaction has held its lock without a break) and the held flag must not have lapsed. A write that fails this may have landed after a reset elsewhere, so it is quarantined: the credential gets the hash of a random secret, every session, pending two-factor challenge and CLI credential is revoked, and the request fails with 409 `PASSWORD_WRITE_UNCONFIRMED` and no cookie. The account owner recovers with Forgot password. The lock order is password-write, then cli-credentials, then set-password-link; nothing that holds a later lock waits for an earlier one, and nothing inside a password write takes the password-write lock again. The fence takes no lock and no transaction. Two windows stay open by design: a session that existed when the reset ran can still answer from the 60 s cookie cache, and a two-factor disable that raced a reset may still have turned the factor off (it gets no session; the user re-enrols after signing in).

## Password reset sweeps and accepted residuals

The app already revoked sessions and CLI credentials on reset, fenced password sign-ins and session rotations, and serialized password writes. The reset before-hook now checks link eligibility before deletion can change invite eligibility, then revokes all owned sessions, sessions with `impersonatedBy` equal to the user, API keys and device codes under the credential lock. It deletes pending 2FA challenges, their OTPs/attempt counters, credential-fence rows and trusted devices together. Lookup failure or three exhausted sweep attempts returns 503 before consuming the link or changing the password; the form retains both entries and retries the same link. Earlier revocation may already have succeeded, so this does not promise existing credentials survived.

`onPasswordReset` sweeps again after commit, still deleting every session for the app's sign-in fence. Other reset links are cleaned up under the set-password-link lock with an independent retry budget, even when the sweep fails. Mailbox proof and competing-link retirement have already committed atomically with the password before the post-sweep starts; a post-sweep failure cannot undo them. A post-commit error needs a fresh reset link. Logs contain the user id and error class, never error messages or credentials. State-changing Better Auth requests validate the signed token's database session before using cookie-cached data; missing/expired rows return 401 with cleared cookies, lookup failures return 503 without renewing them. The cookie cache remains enabled with its existing 60-second max-age. Change-password retains Better Auth's newly issued caller session and the app's existing password-write lock.

Accepted residuals: an attacker who still knows the old password could sign in and mint a key between the pre-sweep and password commit. Only if every post-sweep attempt also fails can that key survive; the SECURITY log then requires operator revocation. Refusing mints whenever any reset link exists would let anyone who knows an email block that user's keys for an hour. Requests already authenticated and in flight may finish after reset, and read-only cookie-cache answers can persist for up to 60 seconds. This app goes beyond the template residual: its password fingerprint/session-parent fences and password-write locks prevent old-password sign-ins, rotations and concurrent password changes from surviving or overwriting a completed reset. Those protections remain in place; revocation cannot undo work a request already completed.

## Admin access changes

The Users page confirms promotion/demotion with the target's name and email. `users.setRole`, `users.archive`, and `users.remove` share `withAdminRemovalGuard`: target read, active verified admin count and write run in a Serializable transaction. The last active verified admin cannot be removed; serialization conflicts are retryable. Multi-role matching and expired-ban semantics mirror the existing auth helpers. Stable refusal reasons are localized in en-US/es-MX. Successful role changes log one structured `users.role_changed` audit event after commit (this app has no audit table); no-op writes log nothing. Parallel Better Auth role, ban, remove and access-field writes are blocked at the existing admin gate; the app uses oRPC for them.
