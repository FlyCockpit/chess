# Auth and routing

Session guards and identity rules for the web app (`apps/web`). The template's `patterns/auth-and-routing.md` has the full routing guide; this file records how this app applies its identity rules.

## Query cache follows identity

The TanStack Query cache, module state and every in-flight request callback belong to one identity: the one the document was used by. `apps/web/src/lib/document-identity.ts` keeps that identity at module scope for the whole life of the document (never in a component, which a remount would make forget). When a confirmed identity differs from it, the document is replaced with a full load. A page load is asynchronous, so every replacement first quarantines the document synchronously: the page is hidden and the QueryClient sealed (emptied, and anything a late callback adds is removed again), so nothing of the previous identity stays on screen while the new page loads.

| Transition | What happens |
|---|---|
| Explicit sign-out (the account menu, `user-menu-content.tsx`) | `signOutAndLeave()` (`apps/web/src/lib/explicit-sign-out.ts`): marks the sign-out, then on success `leaveDocument()` to login, a fresh document with an empty cache. A failure (returned or thrown) undoes the mark; add any new sign-out button through it. |
| Signed out elsewhere (another tab, expiry, revocation) | The document reloads in place; the guards send the visitor to login. |
| Another account (same tab or another tab) | The document reloads in place; the guards admit the new account and its queries load fresh. |
| Anonymous → signed in | Nothing: an anonymous cache holds only public data, so password sign-in keeps its client-side navigate. |
| `pending` / `error` | Never acted on: a flaky session check must not reload a signed-in page. |

Three observers feed it, and none can be skipped:

- **Every session guard** (`_auth`, `admin`, `login`, `signup`, `forgot-password`, `reset-password`) calls `resolveRouteSession()` (`apps/web/src/lib/route-session.ts`): `getRouteSession()`, then the identity check. A different identity replaces the document and the guard never settles, so no page under it renders the previous identity's cached data. An answer to a probe that started before a newer identity was recorded (a hover preload sent before this tab signed in) is out of date: the guard probes again and uses only the fresh answer. `pnpm policy:checks` rejects any route-file reference to `getRouteSession` or `@/server/auth-session`.
- **The watcher**, `useReloadOnIdentityChange()`, for a change while a page is open. The `_app` shell frame runs it eagerly (`AppShellFrame` in `routes/$lang/_app/route.tsx`, shared by the pending shell and the loaded one), so it is connected before the shell shows the account or any guarded page renders. The hosted root also mounts it through `IdentityBoundary` (`apps/web/src/components/identity-boundary.tsx`), loaded lazily on the first account-aware page (any `_app` page, or the public Studio tab, `useIdentityBoundaryEnabled`) and kept mounted across public navigation, so it also covers the public pages. Both share the document's baseline and its one reload. The Studio tab is private UI that no guard covers, so it shows and fetches its admin data only once the document has recorded the signed-in account (by a guard or the watcher) and the watcher is connected (`useDocumentAdmits`); until then it shows its skeleton, never a cache the previous account filled before anything was watching. A peer's announcement or a 401 that arrives before the lazily loaded watcher connects is remembered and checked as soon as it does. It runs in a layout effect, before a frame pairs the new chrome with the old data. It also connects the open tabs: Better Auth tells other tabs about a sign-out but not a sign-in, so each newly confirmed identity (seen by the watcher or by any guard) is announced on the document's `BroadcastChannel`, the auth client announces every session change made in the tab (`$sessionSignal`: sign-in, sign-up, 2FA) before the flow navigates, and SSO returns through the login guard. Every other tab with a watcher re-checks its session.
- **The global error toasts** (`apps/web/src/router.tsx`): before any toast opt-out, a query rejected with 401 asks Better Auth to check the session (one check in flight at a time) instead of toasting; a mutation still toasts. Nothing toasts once the document is being replaced.

The router also covers the back/forward cache: a document that ever held a signed-in user's state (recorded by a guard or the watcher, or a signed-in session seen by `useAuthSession`, so a fresh `verify-email` page counts too) is hidden as it enters the cache and reloaded when restored, so Back never shows a frozen page nobody re-checked. Anonymous pages are cached as usual.

Persisted client storage holds no private data: `localStorage` keeps only device choices (locale, theme, consent) and `sessionStorage` the stale-build recovery cooldown. The CLI local lab (`apps/web/src/local.tsx`) is a separate document with its own QueryClient and no Better Auth session, so none of this applies there. A new store of private data in browser storage needs its own identity scoping or clearing.

Why a full load, not `queryClient.clear()` or a fresh `QueryClient`: clearing the cache while observers are mounted cancels their fetches silently and can leave the page stuck on a skeleton, `resetQueries()` refetches active queries as the wrong identity, and neither stops an in-flight mutation whose late `onSuccess` writes the old identity's data back. A swapped client still leaves module state behind. A full load drops all of it, and a late callback can only write into the document being discarded.
